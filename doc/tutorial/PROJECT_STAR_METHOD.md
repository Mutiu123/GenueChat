# GenueChat - STAR Method Project Overview

## Situation

GenueChat was conceived to address the growing demand for enterprise-grade AI-powered chatbot solutions that can both handle general conversational queries and provide document-grounded answers from uploaded PDF files. Organizations increasingly need intelligent assistants that integrate seamlessly into existing infrastructure, maintain strict security postures, and scale reliably under production workloads. The project needed to bridge the gap between prototype-level LLM applications and fully production-ready, observable, and secure API services.

Key contextual factors:

- Enterprises require conversational AI that can reference internal documents without exposing data to third-party services beyond the LLM inference layer.
- Existing chatbot solutions often lack proper authentication, rate limiting, audit logging, and monitoring out of the box.
- There was a need for a RESTful API-first design that can be consumed by multiple frontend clients, internal tools, and third-party integrations.
- The chosen LLM backend (Groq with Llama 3.1 8B) provides fast inference at low cost, but the application layer must handle async orchestration, error resilience, and observability on its own.
- Deployment targets span local development, Docker containers, Heroku, and Kubernetes clusters, requiring a flexible and reproducible infrastructure setup.
- Code quality enforcement through linting, type checking, formatting, and pre-commit hooks was essential from the start to maintain long-term maintainability.

---

## Task

The objective was to design, implement, test, and deploy a production-ready Retrieval-Augmented Generation (RAG) chatbot API with the following requirements:

- Build a FastAPI-based REST API exposing endpoints for general chat, document-based Q&A, authentication, and health checks under a versioned `/api/v1` prefix.
- Implement a RAG pipeline using LangChain, FAISS vector store, HuggingFace embeddings, and Groq LLM inference to allow users to upload PDF documents and ask questions grounded in their content.
- Establish JWT-based authentication (HS256) with configurable token expiration and a `get_current_user` dependency to protect all chat endpoints.
- Implement per-IP token-bucket rate limiting to prevent abuse and ensure fair resource allocation across clients.
- Design a layered exception handling system with custom exception classes mapped to semantic HTTP status codes (400, 401, 403, 422, 429, 502, 503) and global error handlers that include request tracing IDs.
- Integrate Prometheus metrics collection (11 metric types covering HTTP requests, LLM predictions, document uploads, database operations, auth events, and errors) with a Grafana dashboard for visualization.
- Set up structured JSON logging to stdout with audit logging for authentication events and LLM prediction details.
- Implement input sanitization against XSS and NoSQL injection attacks on all user-facing inputs.
- Provide MongoDB integration via the Motor async driver with connection pooling, health checks, and a singleton pattern for shared access.
- Create a comprehensive test suite targeting 80% or higher code coverage using pytest, pytest-asyncio, and pytest-cov.
- Configure CI/CD via GitHub Actions with sequential lint, test, and Docker build stages.
- Provide Kubernetes deployment manifests including Deployment, Service, HorizontalPodAutoscaler, NetworkPolicy, and Ingress resources.
- Containerize the application with multi-stage Docker builds, non-root user execution, and built-in health checks.
- Support multiple deployment targets: local development with hot-reload, Docker Compose with full monitoring stack, Heroku via Procfile, and Kubernetes for production orchestration.

## Action

The implementation followed a deliberate, step-by-step approach. Each major subsystem was built with specific technical rationale, and at every decision point I evaluated alternative approaches before committing to a direction. The following sections walk through exactly how the project was constructed, what alternatives existed, and why each choice was made.

### Step 1 -- Choosing the Web Framework and Application Architecture

The first decision was selecting the web framework. The three primary candidates were Flask, Django REST Framework, and FastAPI.

- I chose FastAPI over Flask because FastAPI provides native async/await support built on Starlette and ASGI, which is critical for a chatbot API where LLM inference calls can block for seconds. Flask runs on WSGI, which is synchronous by default. Achieving true async behavior in Flask requires additional libraries like Quart or running behind Celery for background tasks, adding complexity without native integration. FastAPI also generates OpenAPI documentation automatically from type hints and Pydantic models, eliminating the need for separate Swagger configuration or libraries like flask-restx.
- I chose FastAPI over Django REST Framework because Django carries the weight of its ORM, admin interface, template engine, and migration system, none of which are needed for a stateless API service. Django REST Framework adds serializer classes on top of that. For a focused API with no server-rendered templates and no relational database models, Django would introduce unnecessary overhead. FastAPI's dependency injection system (using Depends) provides a cleaner mechanism for cross-cutting concerns like authentication and rate limiting than Django's middleware class hierarchy.
- I selected Uvicorn as the ASGI server rather than Hypercorn or Daphne. Uvicorn is the reference ASGI server recommended by FastAPI's own documentation, has the most mature integration with FastAPI's lifespan protocol, and supports multi-worker mode via the --workers flag. Hypercorn supports HTTP/2 natively which Uvicorn does not, but HTTP/2 was not a requirement for this project and would add TLS configuration complexity at the application layer that is better handled by the Kubernetes Ingress controller. I configured 4 workers for production to utilize multiple CPU cores, and a single worker with --reload for development to enable hot-reloading on file changes.
- I structured the application entry point in app.py using FastAPI's asynccontextmanager-based lifespan protocol rather than the older on_event("startup") and on_event("shutdown") decorators. The lifespan approach was chosen because the on_event decorators are deprecated in FastAPI 0.109+ and because the context manager pattern guarantees that shutdown logic runs even if startup raises an exception, which the decorator-based approach does not guarantee. Inside the lifespan, I call db.connect() wrapped in a try/except so that the application can still start and serve health check endpoints even when MongoDB is temporarily unavailable, rather than crashing on startup.
- I organized the source code into a src/ package with 10 dedicated modules (config.py, database.py, exceptions.py, llm.py, middleware.py, monitoring.py, prompts.py, schemas.py, security.py) and a routes/ subpackage with three routers (health.py, auth.py, chat.py). The alternative was a flat structure with everything in app.py or a Django-style apps/ directory. I chose the single-package layout because the application is a single bounded context (a chatbot API), not a collection of independent apps, and this structure keeps imports straightforward (from src.security import get_current_user) without circular dependency risks.
- All routes are mounted under the /api/v1 prefix using FastAPI's include_router with a prefix parameter. I chose URL-path versioning (/api/v1) over header-based versioning (Accept-Version) or subdomain-based versioning (v1.api.example.com) because path versioning is the most explicit and debuggable approach: it is visible in logs, curl commands, and browser developer tools. Header-based versioning is harder to test casually and can be stripped by intermediate proxies. Subdomain versioning requires DNS configuration changes for each version.
- I conditionally disable the /docs and /redoc endpoints in production by setting docs_url and redoc_url to None when settings.is_production returns True. The OpenAPI specification is still generated internally (used by the custom_openapi function for development), but the interactive documentation pages are not exposed on production deployments to reduce the attack surface and prevent information disclosure about internal API structure.
- I added a custom_openapi() function that overrides FastAPI's default schema generation. This function caches the generated schema on app.openapi_schema after the first call and adds an x-logo extension to the info section. The alternative was to let FastAPI auto-generate the schema on every /openapi.json request, but caching avoids regenerating the schema on each call, which involves reflecting all routes and their type annotations.

### Step 2 -- Configuration Management

- I built a centralized Settings class in config.py using Pydantic v2's BaseSettings (from the pydantic-settings package). The alternative was to use raw os.getenv() calls scattered throughout the codebase, python-decouple, or a YAML/TOML configuration file. I chose Pydantic BaseSettings because it provides automatic type coercion (string environment variables are cast to int, float, bool, or Enum types), validation at startup (the application fails fast with a clear error if a required setting is missing or invalid), and a single source of truth for all configuration rather than getenv calls spread across modules. Python-decouple provides similar environment loading but lacks built-in type validation and does not integrate with Pydantic's model serialization.
- The Settings class defines over 30 parameters organized into five groups: Application (APP_NAME, APP_VERSION, ENVIRONMENT, DEBUG, HOST, PORT, LOG_LEVEL), Security (SECRET_KEY, JWT_ALGORITHM, JWT_EXPIRATION_MINUTES, CORS_ORIGINS, RATE_LIMIT_REQUESTS, RATE_LIMIT_WINDOW_SECONDS), Database (MONGODB_URL, MONGODB_DATABASE, MONGODB_MIN_POOL_SIZE, MONGODB_MAX_POOL_SIZE, MONGODB_TIMEOUT_MS), LLM (GROQ_API_KEY, LLM_MODEL_NAME, LLM_TEMPERATURE), and Monitoring (PROMETHEUS_ENABLED, METRICS_PREFIX). Every parameter has a sensible default so the application can start with zero configuration for local development, but production deployments override these via environment variables.
- I defined an Environment enum (DEVELOPMENT, STAGING, PRODUCTION) as a string enum (str, Enum) rather than using raw strings. This prevents typos like "producton" from silently being accepted. Pydantic validates the environment variable value against the enum members and raises a clear validation error if the value does not match. The enum also enables typed property checks like is_production and is_development that drive conditional behavior throughout the application, such as disabling the OpenAPI docs UI, suppressing access logs, and adjusting log levels.
- The Settings instance is created through a get_settings() function decorated with functools.lru_cache(). This ensures that no matter how many modules import and call get_settings(), only one Settings object is ever instantiated. The alternative was to create a module-level singleton (settings = Settings()), but lru_cache is preferable because it can be cleared in tests using get_settings.cache_clear(), allowing each test to start with fresh configuration after monkeypatching environment variables. A module-level singleton would be frozen at import time and would not reflect test-specific overrides.
- I added a field_validator for CORS_ORIGINS that splits the comma-separated string and validates that at least one origin is present. The cors_origins_list property splits the string into a Python list on demand. I stored CORS origins as a single comma-separated string rather than a JSON array because environment variables are inherently strings, and a comma-separated format is simpler to configure in Docker Compose env_file directives and Kubernetes ConfigMaps without worrying about JSON escaping.
- The model_config dictionary sets env_file=".env", env_file_encoding="utf-8", and case_sensitive=True. The case_sensitive setting is important because Pydantic v2 defaults to case-insensitive matching, which means an environment variable named secret_key (lowercase) would silently map to SECRET_KEY. Enforcing case sensitivity prevents accidental mismatches between environment variable names and field names.

### Step 3 -- Database Layer

- I chose MongoDB over PostgreSQL or SQLite as the database for this project. The primary data stored is audit logs and session metadata, which are inherently document-shaped (nested JSON with variable schemas per event type). MongoDB's schemaless document model fits this use case naturally without requiring ALTER TABLE migrations when the audit payload structure evolves. PostgreSQL would require either a rigid schema with frequent migrations or a JSONB column that negates most of the benefits of a relational database. SQLite was ruled out because it does not support concurrent writes from multiple Uvicorn workers, which would cause database-locked errors under load.
- I selected Motor (motor.motor_asyncio) as the MongoDB driver rather than PyMongo directly. Motor is an async wrapper around PyMongo that integrates with Python's asyncio event loop. Since FastAPI route handlers are async functions and the entire application runs on an ASGI event loop, using synchronous PyMongo calls would block the event loop during every database operation (connection, query, insert). Motor's AsyncIOMotorClient performs all I/O operations asynchronously, allowing the event loop to continue processing other requests while waiting for MongoDB responses. The alternative of running PyMongo in a thread pool via run_in_executor would work but adds unnecessary complexity when a purpose-built async driver exists.
- I implemented the Database class as a singleton using Python's __new__ method. The __new__ method checks if _instance is None and only creates a new object on the first call; subsequent calls return the same instance. I chose __new__-based singleton over module-level instantiation because it allows the Database class to be imported without immediately establishing a connection. The actual connection is established only when connect() is called during the application lifespan. The alternative of using a module-level global variable (db = AsyncIOMotorClient(...)) would attempt to connect at import time, which fails during testing and during Docker image builds when MongoDB is not available.
- Connection pooling is configured with minPoolSize=10 and maxPoolSize=50. The minimum of 10 ensures that the application maintains a warm pool of connections even during idle periods, avoiding the latency of establishing new TCP connections when traffic resumes. The maximum of 50 prevents a single application instance from exhausting MongoDB's connection limit (default 65536) even when running multiple Uvicorn workers. These values are configurable through MONGODB_MIN_POOL_SIZE and MONGODB_MAX_POOL_SIZE environment variables. The alternative of relying on Motor's default pool settings (minPoolSize=0, maxPoolSize=100) would result in cold-start latency after idle periods and potential connection exhaustion in multi-worker deployments.
- The connect() method verifies connectivity by issuing an admin.command("ping") after creating the client. This catches configuration errors (wrong hostname, authentication failures, network issues) at startup rather than on the first user request. The health_check() method reuses the same ping command for Kubernetes readiness probes. If the ping fails, health_check returns False rather than raising an exception, allowing the health endpoint to return a structured "unhealthy" response instead of a 500 error.
- Both serverSelectionTimeoutMS and connectTimeoutMS are set to 5000 milliseconds (configurable via MONGODB_TIMEOUT_MS). Without explicit timeouts, the Motor driver defaults to 30 seconds for server selection, meaning a route handler could hang for 30 seconds if MongoDB becomes unreachable. A 5-second timeout ensures that database failures surface quickly and the application can return a 503 error to the client within a reasonable timeframe.
- The close() method sets both _client and _db to None after closing the client, ensuring that any subsequent access to the client or db properties raises a RuntimeError with a clear message rather than operating on a closed connection. This is called during the lifespan shutdown phase to release connection pool resources cleanly.

### Step 4 -- LLM and RAG Pipeline Implementation

- I chose LangChain as the LLM orchestration framework rather than calling the Groq API directly via the requests library or using LlamaIndex. Calling the Groq REST API directly would work for simple single-turn inference, but it would require manually implementing conversation memory management, document chunking, embedding generation, vector storage, retrieval logic, and prompt template composition. LangChain provides all of these as composable abstractions. LlamaIndex was the other major alternative; it is more opinionated toward document indexing and retrieval and offers a simpler "query engine" abstraction. However, LangChain's pipe-based chain composition syntax (retriever | prompt | llm | parser) provides more flexibility for customizing each pipeline stage independently, and LangChain has broader community adoption and plugin availability for various LLM providers including Groq.
- I selected Groq as the LLM inference provider with the Llama 3.1 8B Instant model. The alternatives were OpenAI GPT-4/GPT-3.5, Anthropic Claude, or self-hosted models via Ollama or vLLM. Groq was chosen because it offers the fastest inference latency among cloud LLM providers (typically under 500ms for short responses) due to its custom LPU (Language Processing Unit) hardware. For an enterprise chatbot API where response time directly impacts user experience, inference speed was prioritized. OpenAI GPT-4 provides higher quality responses but at 10-20x higher latency and cost. Self-hosted models via Ollama or vLLM would eliminate API dependency but require GPU infrastructure provisioning and maintenance. The model is configurable via the LLM_MODEL_NAME environment variable, so switching to a different Groq-hosted model (Llama 3.1 70B, Mixtral 8x7B) requires only a configuration change.
- The LLM temperature is set to 0.0 for deterministic, reproducible responses. In an enterprise setting, users expect consistent answers to the same question. A temperature of 0.0 causes the model to always select the highest-probability token, eliminating randomness. The alternative of using a higher temperature (0.3-0.7) would produce more varied and creative responses but at the cost of consistency and predictability, which is unacceptable for production systems where audit logging records the exact question and answer for compliance purposes.
- The get_llm() function is decorated with @lru_cache() to ensure only one ChatGroq client instance is created across the entire application lifetime. Without caching, every incoming request would instantiate a new ChatGroq object, which involves initializing the HTTP client, validating the API key, and setting up retry logic. The lru_cache ensures this initialization happens exactly once. The API key resolution follows a priority chain: first it tries get_settings().GROQ_API_KEY (the Pydantic-validated configuration), then falls back to os.getenv("API") and os.getenv("GROQ_API_KEY") for backward compatibility with the earlier prototype that used a different environment variable name.
- For general conversation, I implemented a ConversationChain with ConversationBufferMemory. The ConversationBufferMemory stores the complete conversation history as a growing string of "Human: ... AI: ..." turns. The alternative memory strategies were ConversationSummaryMemory (which summarizes older turns to save context window space), ConversationBufferWindowMemory (which keeps only the last N turns), or ConversationTokenBufferMemory (which truncates based on token count). I chose BufferMemory because the Llama 3.1 8B model has a 128K token context window, which is large enough to hold extensive conversation histories without truncation for typical enterprise chat sessions. Summary memory would lose important details from earlier turns, and window memory would create an artificial cutoff. The conversation prompt template uses {history} and {input} placeholders, where LangChain's memory automatically injects the accumulated conversation history into {history} before each LLM call.
- The RAG pipeline for document Q&A is implemented across three functions: load_and_retrieve(), rag_chain(), and the async wrapper rag_chain_async(). The pipeline follows the standard RAG pattern: load, split, embed, store, retrieve, generate. I chose this sequential in-request pipeline rather than a pre-indexing approach (where documents are uploaded and indexed separately from queries) because the project requirements specify per-request document upload. Each uploaded PDF is processed fresh on every request. A pre-indexing approach with persistent vector storage would be more efficient for repeated queries against the same document, but would require session management to track which user uploaded which document and a background worker to handle indexing asynchronously.
- For PDF parsing, I used LangChain's PyPDFLoader, which wraps the pypdf library. The alternatives were pdfplumber (better table extraction), pdfminer.six (lower-level control), or unstructured (multi-format support). PyPDFLoader was chosen because it handles the common case of extracting text from standard PDF documents reliably, has minimal dependencies, and integrates directly with LangChain's Document schema. For PDFs with complex layouts, tables, or scanned images, a more sophisticated parser like unstructured with OCR support would be needed, but that falls outside the current scope.
- Text splitting uses RecursiveCharacterTextSplitter with chunk_size=1000 and chunk_overlap=200. The chunk size of 1000 characters was chosen to balance between providing enough context per chunk for meaningful retrieval (too small and the chunks lack coherent information) and staying well within embedding model token limits (the default HuggingFace sentence-transformers model handles sequences up to 512 tokens, roughly 2000 characters). The 200-character overlap ensures that sentences split across chunk boundaries are present in both adjacent chunks, preventing information loss at split points. The alternative splitter was TokenTextSplitter (which splits based on token count rather than character count), but character-based splitting is faster and produces comparable results for English text where character-to-token ratios are relatively stable.
- For embedding generation, I used HuggingFaceEmbeddings, which defaults to the all-MiniLM-L6-v2 model from the sentence-transformers library. The alternatives were OpenAI's text-embedding-ada-002 (higher quality but requires an API call and adds latency and cost per request), Cohere embeddings, or a locally-hosted larger model. The HuggingFace model runs locally in-process, meaning embedding generation does not depend on any external API and does not incur per-request costs. The all-MiniLM-L6-v2 model produces 384-dimensional embeddings and is optimized for speed, making it suitable for real-time document processing within an API request cycle. The trade-off is that larger embedding models (like all-mpnet-base-v2 with 768 dimensions) produce higher-quality embeddings for semantic search, but the latency increase is not justified for the typical enterprise document Q&A use case.
- I chose FAISS (Facebook AI Similarity Search) as the vector store rather than ChromaDB, Pinecone, Weaviate, or Qdrant. FAISS runs entirely in-memory with no external service dependency, which simplifies deployment and eliminates network latency for similarity search. ChromaDB provides persistence and metadata filtering but requires a separate server process or embedded database. Pinecone and Weaviate are managed cloud services that add external dependencies and per-query costs. Since each document is processed within a single request and the vector index is not persisted across requests, FAISS's in-memory approach is the most efficient choice. The index is created from documents using FAISS.from_documents() and immediately used as a retriever via vectorstore.as_retriever(), then garbage-collected when the request completes.
- The RAG chain is composed using LangChain's pipe operator syntax: {"context": retriever, "question": RunnablePassthrough()} | prompt | get_llm() | StrOutputParser(). This declarative composition creates a pipeline where the retriever fetches relevant document chunks based on the question, the prompt template injects those chunks as {context} alongside the {question}, the LLM generates an answer grounded in the context, and the StrOutputParser extracts the string response from the LLM's message object. The alternative was to use LangChain's RetrievalQA chain (a higher-level abstraction), but the pipe-based approach provides more explicit control over each step and is the recommended pattern in LangChain v0.2+.
- The document prompt template explicitly instructs the model to "Answer the question based only on the following context," which constrains the model to ground its answer in the retrieved document chunks rather than relying on its parametric knowledge. This reduces hallucination risk for document Q&A. The general chat template uses a simpler format with {history} for conversation context and {input} for the current message, allowing the model to respond freely using its training knowledge.
- All LLM and RAG calls are wrapped in async functions (handle_chat_async, rag_chain_async) that use asyncio.get_event_loop().run_in_executor(None, lambda: ...) to run the synchronous LangChain operations in a thread pool. This is necessary because LangChain's ConversationChain.predict() and chain.invoke() are synchronous blocking calls. If called directly from an async FastAPI route handler, they would block the entire event loop for the duration of the LLM inference (potentially several seconds), preventing all other requests from being processed. By offloading to the default ThreadPoolExecutor, the event loop remains free to handle concurrent requests. The alternative was to use LangChain's ainvoke() async methods, but at the time of implementation, the async support in LangChain's Groq integration and conversation chain was not fully stable, and the executor approach is a reliable, well-understood pattern.
- In the document chat route handler, uploaded PDF files are written to a temporary file using tempfile.NamedTemporaryFile(delete=False, suffix=".pdf"). PyPDFLoader requires a filesystem path (it does not accept a bytes buffer or file-like object), so the upload must be materialized to disk. The delete=False flag is set because the file must remain available for PyPDFLoader to read after the with block closes the NamedTemporaryFile handle. Cleanup is handled in a finally block using os.unlink(tmp_path) to ensure the temporary file is removed even if the RAG pipeline raises an exception. The alternative of using an in-memory PDF parser (like pdfplumber with BytesIO) would avoid disk I/O but would require replacing PyPDFLoader with a different document loading approach that LangChain does not natively support.

### Step 5 -- Exception Handling Architecture

- I designed a custom exception hierarchy rooted in GenueException, with seven specialized subclasses: AuthenticationError (401), AuthorizationError (403), RateLimitError (429), ValidationError (422), DatabaseError (503), LLMError (502), and DocumentProcessingError (400). The alternative was to use FastAPI's built-in HTTPException for all error cases, passing different status codes. I chose custom exceptions because they provide semantic meaning in the codebase (raise LLMError("Failed to generate response") is more readable and greppable than raise HTTPException(status_code=502, detail="Failed to generate response")), they allow attaching structured details dictionaries for machine-readable error information, and they can be caught and handled differently by the global exception handlers.
- The GenueException base class accepts message, status_code, and an optional details dictionary. The details field allows exceptions to carry structured metadata (for example, ValidationError can include a dictionary of field-level validation errors) that is serialized into the JSON error response. HTTPException's detail field is a single string, which is less structured.
- I registered four global exception handlers on the FastAPI application via register_exception_handlers(). The handler for GenueException extracts the request_id from request.state (set by RequestIDMiddleware) and includes it in the error response, enabling correlation between client-facing errors and server-side logs. The handler for RequestValidationError converts Pydantic validation errors into a structured format with the errors list nested under a details key, rather than returning FastAPI's default validation error format. The catch-all Exception handler returns a generic "Internal server error" message with status code 500, deliberately hiding internal exception details from the client to prevent information leakage. In a production environment, stack traces and internal error messages should never be exposed to external clients.
- Each error response follows a consistent schema: {"error": true, "status_code": int, "message": str, "details": dict|null, "request_id": str|null}. The error boolean field allows clients to reliably detect error responses without relying solely on HTTP status codes, which is useful for clients that process response bodies before checking status codes. The request_id field is included in every error response so that users can reference it when contacting support, and support engineers can grep server logs for that specific request ID to diagnose the issue.
- The HTTP status codes for each exception subclass were chosen according to RFC 9110 semantics. 401 (Unauthorized) for AuthenticationError signals that the request lacks valid credentials. 403 (Forbidden) for AuthorizationError signals that the server understood the request but refuses to authorize it. 429 (Too Many Requests) for RateLimitError signals rate limiting per RFC 6585. 422 (Unprocessable Content) for ValidationError signals that the request body is syntactically valid JSON but fails semantic validation. 502 (Bad Gateway) for LLMError signals that the application received an invalid response from the upstream LLM service (Groq). 503 (Service Unavailable) for DatabaseError signals that a dependent service (MongoDB) is temporarily unavailable. 400 (Bad Request) for DocumentProcessingError signals that the client-supplied document is malformed or unsupported.
- The _error_response helper function constructs a JSONResponse with the consistent error schema. It conditionally includes the details and request_id fields only when they are not None, keeping successful error responses compact. The function is shared across all four exception handlers to eliminate response format inconsistencies.
- The exception handler for the generic Exception base class (the catch-all handler) deliberately does not log the exception details to the response. Instead, it returns only "Internal server error" with status code 500. The actual exception details are logged server-side via the logger.exception() call in the route handler's except block. This separation ensures that unexpected errors (programming bugs, third-party library failures, infrastructure issues) are captured in the logs for debugging but are never leaked to external clients, preventing information disclosure vulnerabilities.
- Each custom exception class uses a default message that describes the error category (for example, AuthenticationError defaults to "Authentication failed" and DatabaseError defaults to "Database error"). Callers can override these with more specific messages when raising exceptions (for example, raise AuthenticationError("Token has expired")). This two-tier messaging approach provides useful defaults for generic error cases while allowing specific error context when the caller has additional information.

### Step 6 -- Security Implementation

- I implemented JWT (JSON Web Token) authentication using the PyJWT library with HS256 (HMAC-SHA256) signing. The alternatives were RS256 (RSA asymmetric signing), OAuth2 with an external identity provider (Auth0, Keycloak), or API key-based authentication. I chose HS256 JWT for this implementation because it is the simplest stateless authentication mechanism that provides token expiration and claim-based identity without requiring an external service. RS256 would be appropriate in a microservices architecture where multiple services need to verify tokens without sharing the secret key (they would share only the public key), but GenueChat is a single service that both issues and verifies tokens, making symmetric signing sufficient. OAuth2 with an external provider would be the production choice for real user authentication, and the auth route is explicitly documented as a placeholder to be replaced with real credential verification when integrating with an identity provider.
- The create_access_token() function constructs a JWT payload with three standard claims: sub (subject, the username), exp (expiration timestamp), and iat (issued-at timestamp). Both timestamps use datetime.now(timezone.utc) to ensure timezone-aware UTC timestamps, avoiding the pitfalls of naive datetime objects that can produce incorrect expiration calculations when the server timezone differs from UTC. The function returns a tuple of (token_string, expires_in_seconds) so that the API response can inform the client exactly when the token will expire. The expiration is configurable via JWT_EXPIRATION_MINUTES (default 60 minutes).
- The verify_token() function calls jwt.decode() with the algorithms parameter explicitly set to [settings.JWT_ALGORITHM]. The algorithms parameter is a critical security requirement: without it, an attacker could craft a token with the "none" algorithm or switch to RS256 using the HS256 secret as a public key, bypassing signature verification. PyJWT requires this parameter and raises an error if it is missing, but explicitly passing it is defensive coding practice. The function catches ExpiredSignatureError and InvalidTokenError separately to provide specific error messages to the client.
- The get_current_user() dependency uses FastAPI's HTTPBearer scheme with auto_error=False. Setting auto_error to False means that if no Authorization header is present, FastAPI returns None to the dependency instead of automatically raising a 403 error. This allows the dependency to raise a custom AuthenticationError (401) with a "Missing authorization header" message, maintaining consistent error response formatting with the GenueException hierarchy rather than mixing in FastAPI's default error format.
- I implemented rate limiting using a token-bucket algorithm rather than a fixed-window or sliding-window counter. In the fixed-window approach, a counter resets at the start of each time window (for example, every 60 seconds), which creates a burst vulnerability at window boundaries: a client could make 100 requests at 59.9 seconds and another 100 at 60.1 seconds, effectively doubling the intended rate within a 1-second span. The token-bucket algorithm avoids this by refilling tokens continuously based on elapsed time. Each client IP gets a bucket initialized at max_tokens (default 100). On each request, the bucket is refilled proportionally to the time elapsed since the last request (elapsed_seconds * max_tokens / window_seconds), then one token is consumed. If the bucket has fewer than 1 token, the request is rejected with a 429 RateLimitError. The sliding-window log approach (tracking timestamps of every request) would provide the most accurate rate limiting but requires storing individual request timestamps per client, which consumes more memory. The token-bucket is O(1) memory per client.
- The rate limiter state is stored in-memory using a dictionary (_buckets) mapping client IP strings to (tokens, last_time) tuples. This means rate limiting is per-process rather than globally distributed. In a multi-worker or multi-pod deployment, each worker maintains its own independent rate limiter state, so the effective rate limit is multiplied by the number of workers. For true distributed rate limiting, the state would need to be stored in Redis (using redis-py with atomic INCR operations) or a similar shared store. The in-memory approach was chosen for simplicity and zero external dependencies. If distributed rate limiting becomes a requirement, the TokenBucketRateLimiter class can be replaced with a Redis-backed implementation without changing the check_rate_limit dependency interface.
- The rate limiter uses time.monotonic() rather than time.time() for measuring elapsed time. time.monotonic() returns a clock value that always moves forward and is not affected by system clock adjustments (NTP corrections, daylight saving changes, manual clock changes). time.time() can jump backward if the system clock is adjusted, which would cause the token refill calculation to produce negative elapsed times and incorrectly deny legitimate requests.
- Input sanitization is implemented through two functions with compiled regex patterns. sanitize_input() applies three transformations in sequence: first, it removes <script>...</script> blocks including their content (using a compiled regex with re.I | re.S flags for case-insensitive and dotall matching); second, it strips all remaining HTML tags (using a compiled regex matching <[^>]+>); third, it escapes remaining HTML entities using html.escape(quote=True) which converts <, >, &, ", and ' to their entity equivalents. The alternative was to use a dedicated HTML sanitization library like bleach or the nh3 Rust-based sanitizer, which provide allowlist-based tag filtering. However, for this application, no HTML is ever valid input (users send plain-text questions), so stripping all tags is the correct approach. A library like bleach would add a dependency for functionality that is not needed.
- sanitize_for_db() removes the characters $, {, and } using a compiled regex. These characters are the building blocks of MongoDB operator injection attacks. For example, an attacker could send {"$gt": ""} as a username field to bypass authentication checks if the value is passed directly to a MongoDB query. By stripping these characters before any database interaction, the attack vector is eliminated. The alternative of using parameterized queries (which MongoDB drivers support) would also prevent injection, but belt-and-suspenders defense-in-depth is appropriate for security-critical code.
- Both regex patterns are compiled once at module import time using re.compile() and stored in module-level variables (_SCRIPT_RE, _TAG_RE, _MONGO_INJECTION_CHARS). The alternative of using re.sub() with inline pattern strings would recompile the regex on every function call. Compiled regex objects are significantly faster for repeated use because the pattern is parsed and optimized once during compilation.
- Pydantic v2 field validators on ChatRequest, DocumentChatRequest, and TokenRequest enforce input constraints at the schema level before the request reaches the route handler. The question field in ChatRequest uses Field(..., min_length=1, max_length=5000) with a @field_validator that strips whitespace and rejects blank strings. This three-layer validation (min_length check on raw input, strip whitespace, reject blank result) prevents edge cases like a question consisting entirely of spaces from reaching the LLM, which would waste inference credits on meaningless queries. The 5000-character maximum was chosen as a balance between allowing detailed questions and preventing abuse through extremely long inputs that could consume excessive LLM context window tokens.
- CORS is configured in setup_middleware() using FastAPI's CORSMiddleware with allow_origins set from the parsed CORS_ORIGINS configuration, allow_credentials=True for cookie-based authentication support, allow_methods covering GET/POST/PUT/DELETE/OPTIONS, allow_headers=["*"] to accept any custom headers, and expose_headers=["X-Request-ID"] to make the request tracing header accessible to browser-based clients. The CORS middleware is added first in the middleware stack (before MetricsMiddleware and RequestIDMiddleware) because CORS preflight OPTIONS requests must be handled before any other middleware processing. If MetricsMiddleware ran first, preflight requests would be counted as regular requests and would inflate the HTTP request metrics.

### Step 7 -- Middleware Pipeline

- The middleware stack consists of three layers added in a specific order in setup_middleware(): CORSMiddleware first, MetricsMiddleware second, and RequestIDMiddleware third. Due to how Starlette's BaseHTTPMiddleware processes the stack, middleware added last executes first on incoming requests. This means RequestIDMiddleware runs first (assigning the X-Request-ID), then MetricsMiddleware (recording timing and status), then CORSMiddleware (handling preflight responses). This ordering is intentional: the request ID must be set before metrics recording so that any errors during metrics processing can reference the request ID, and CORS must run outermost so that preflight OPTIONS requests are handled without triggering authentication or other processing.
- RequestIDMiddleware extends Starlette's BaseHTTPMiddleware and overrides the dispatch method. It checks for an incoming X-Request-ID header and uses that value if present (enabling distributed tracing across microservices), or generates a new UUID4 if the header is absent. The ID is stored on request.state.request_id (making it accessible to route handlers and exception handlers) and added to the response headers. The alternative was to use a context variable (contextvars.ContextVar) instead of request.state, which would allow the request ID to be accessed from anywhere in the call stack without passing the request object. I chose request.state because it is the standard Starlette/FastAPI mechanism for per-request state and does not require understanding contextvars semantics.
- MetricsMiddleware records three Prometheus instruments per request: it increments the ACTIVE_REQUESTS gauge on entry, measures wall-clock latency using time.perf_counter() (which provides the highest resolution monotonic clock available), and on completion records the method/endpoint/status_code on REQUEST_COUNT and method/endpoint on REQUEST_LATENCY. The middleware wraps the call_next(request) invocation in a try/finally block to ensure metrics are always recorded even if the downstream handler raises an exception. The response is initialized to a 500 status code before calling call_next, so that if an unhandled exception occurs, the metrics correctly reflect a 500 response rather than being skipped entirely. The METRICS_AVAILABLE flag is checked at the top of dispatch to skip all instrumentation if prometheus_client is not installed, allowing the application to run without the monitoring dependency in lightweight development environments.
- I chose BaseHTTPMiddleware (Starlette's standard middleware base class) over pure ASGI middleware. Pure ASGI middleware operates directly on the ASGI protocol (scope, receive, send callables) and is more performant because it avoids the overhead of wrapping the request/response in Starlette's Request and Response objects. However, BaseHTTPMiddleware provides a cleaner API (dispatch receives a Request and returns a Response) that is easier to read, maintain, and test. The performance difference is negligible for an application where the dominant latency is LLM inference (seconds), not middleware overhead (microseconds).

### Step 8 -- Monitoring and Observability

- I chose Prometheus with Grafana over alternatives like Datadog, New Relic, or the ELK stack (Elasticsearch, Logstash, Kibana). Prometheus was selected because it is open-source with no per-host licensing costs, runs as a single static binary, and is the de facto standard for Kubernetes monitoring with native integration through pod annotations (prometheus.io/scrape, prometheus.io/port, prometheus.io/path). Datadog and New Relic are SaaS solutions with per-host pricing that can become expensive at scale. The ELK stack is primarily a log aggregation platform and does not natively provide time-series metrics with PromQL-style querying. Grafana was chosen as the visualization layer because it has first-class Prometheus integration and supports auto-provisioning of datasources and dashboards through YAML configuration files mounted as volumes, enabling infrastructure-as-code for the monitoring stack.
- I defined 11 Prometheus metric instruments in monitoring.py with the prefix "genuechat" (configurable via METRICS_PREFIX). Each metric was chosen to answer specific operational questions. REQUEST_COUNT (Counter with method/endpoint/status_code labels) answers "how many requests did each endpoint receive and what proportion failed." REQUEST_LATENCY (Histogram with 10 buckets from 10ms to 10s) answers "what is the latency distribution for each endpoint" and enables percentile calculations (p50, p95, p99). ACTIVE_REQUESTS (Gauge) answers "how many requests are being processed right now" and can detect request queuing. CHAT_PREDICTIONS and CHAT_LATENCY (Counter and Histogram with source label) distinguish between general chat and document Q&A workloads. DOCUMENT_UPLOADS and DOCUMENT_PROCESSING_TIME track document-specific activity. DB_OPERATIONS tracks database usage by operation type and collection. AUTH_EVENTS counts authentication-related events. ERROR_COUNT categorizes errors by type. APP_INFO stores static metadata (version, environment) for dashboard annotations.
- The histogram bucket boundaries were carefully chosen based on expected latency profiles. HTTP request latency uses 10 buckets: 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0 seconds. This provides fine-grained resolution for fast endpoints (health checks at 1-10ms) and coarser resolution for slow endpoints (LLM inference at 1-10s). Chat prediction latency uses 7 buckets: 0.1, 0.5, 1.0, 2.0, 5.0, 10.0, 30.0 seconds, reflecting the expected range of LLM response times. Document processing uses 7 buckets from 0.5 to 60.0 seconds, accounting for the additional time needed for PDF parsing, embedding generation, and FAISS indexing. The alternative of using Prometheus default buckets (0.005 to 10.0) would not capture the full range of document processing times and would waste bucket precision on sub-millisecond ranges that are never reached.
- I chose Counters over Gauges for cumulative metrics (request count, prediction count, error count) because Counters are monotonically increasing and can survive Prometheus server restarts without data loss (Prometheus computes rate() over Counters, and a counter reset is handled gracefully). Gauges are used only for ACTIVE_REQUESTS because this value naturally goes up and down. Using a Gauge for request counts would make rate calculation unreliable because Prometheus cannot distinguish between a counter reset and a legitimate decrease.
- All Prometheus metric definitions are wrapped in a try/except ImportError block. If prometheus_client is not installed, a METRICS_AVAILABLE flag is set to False, and all code that references metrics checks this flag before attempting to record. This allows the application to run without the monitoring dependency, which is useful for lightweight development and testing environments where Prometheus overhead is unnecessary. The alternative of making prometheus_client a hard dependency would force installation even when monitoring is not needed.
- Structured JSON logging replaces Python's default text-based log format. I implemented a custom JSONFormatter class that extends logging.Formatter and overrides the format() method to return a JSON string. Each log line contains: timestamp (ISO 8601 UTC), level, logger name, message, module, function name, line number, request_id (if present on the log record), and exception traceback (if present). The alternative was to use a third-party structured logging library like structlog or python-json-logger. I chose a custom formatter because it avoids adding a dependency for a relatively simple class (approximately 15 lines of code), and it provides full control over the JSON schema. Structlog provides additional features like context binding and processor pipelines, but these were not needed for this application.
- The setup_logging() function clears all existing handlers on the root logger (root.handlers.clear()) before adding the JSON handler. This prevents duplicate log output when running under Uvicorn, which adds its own handlers to the root logger. Without clearing existing handlers, every log message would be emitted twice: once in JSON format and once in Uvicorn's default format. The function also suppresses noisy third-party loggers (uvicorn.access, motor, pymongo) by setting their level to WARNING, preventing routine connection and query logs from cluttering the JSON output.
- Audit logging is implemented through a dedicated logger (genuechat.audit) with two helper functions. log_audit_event() records generic audit entries with event_type, timestamp, request_id, user, and a freeform payload dictionary. log_prediction_audit() specifically records LLM inference events with the question (truncated to 200 characters to prevent PII leakage in logs), answer length (not the full answer, to avoid logging potentially sensitive generated content), model name, processing time in milliseconds, and source (chat or document). The truncation to 200 characters is a deliberate privacy-conscious choice: audit logs may be stored long-term and accessed by operations teams who should not have full visibility into user queries. The alternative was to log the full question and answer, which would provide more debugging information but creates data retention and privacy compliance risks.
- The /metrics endpoint is implemented by mounting the Prometheus ASGI application (make_asgi_app()) at the /metrics path. This endpoint is not protected by authentication or rate limiting because Prometheus scrapers need unauthenticated access to collect metrics. The mounting is conditional on settings.PROMETHEUS_ENABLED being True and prometheus_client being importable, allowing the endpoint to be disabled in environments where metrics collection is handled differently (for example, when using a push-based system like StatsD or when Prometheus is not deployed).

### Step 9 -- API Route Implementation

- The health routes in health.py provide four endpoints designed for different operational purposes. GET /api/v1/health performs a full health check including a MongoDB ping and returns an overall status of "healthy" or "degraded" along with version, environment, uptime, and per-component check results. GET /api/v1/health/live is a lightweight liveness probe that always returns {"status": "alive"} with a 200 status code, used by Kubernetes to determine if the process is running (a non-200 response triggers a pod restart). GET /api/v1/health/ready checks MongoDB connectivity and returns 503 if the database is unreachable, used by Kubernetes to remove the pod from the Service's endpoint list until it recovers. GET /api/v1/status returns application metadata without performing any I/O. The separation between liveness and readiness probes follows Kubernetes best practices: a pod that is alive but not ready should not receive traffic but should not be killed either (it may be waiting for a database connection to be re-established).
- The uptime calculation uses a module-level _start_time = time.time() captured at import time, and each health endpoint computes time.time() - _start_time. The alternative of tracking startup time in the application lifespan would require passing the timestamp through dependency injection, which adds complexity for a simple metric.
- The auth routes in auth.py expose POST /api/v1/auth/token for token generation and GET /api/v1/auth/me for token verification. The token endpoint accepts a TokenRequest body (username and password), creates a JWT via create_access_token(), records an AUTH_EVENTS metric with the "token_issued" label, logs an audit event, and returns the token with its expiration time. The endpoint is protected by check_rate_limit to prevent brute-force credential testing. The route handler currently accepts any non-empty credentials and issues a token, with an explicit docstring noting that real credential verification should be integrated when connecting to an identity provider. This design allows the entire authentication flow to be tested end-to-end during development while clearly marking the placeholder for production integration.
- The chat routes in chat.py expose POST /api/v1/chat/ for general conversation and POST /api/v1/chat/document for document Q&A. Both endpoints require authentication (get_current_user dependency) and rate limiting (check_rate_limit dependency). The general chat endpoint receives a ChatRequest body, sanitizes the question through sanitize_input(), measures inference time using time.perf_counter(), calls handle_chat_async(), logs a prediction audit event, and returns a ChatResponse with the answer, model name, and processing time in milliseconds. The document chat endpoint receives a multipart form with a PDF file upload, a question string, and an optional session_id. It validates that the uploaded file has a .pdf extension, writes the file contents to a temporary file, calls rag_chain_async(), cleans up the temporary file in a finally block, and returns a DocumentChatResponse. Both endpoints catch generic exceptions and re-raise them as LLMError or DocumentProcessingError to ensure consistent error response formatting.
- The dependency injection pattern used across all protected routes follows a consistent structure: dependencies=[Depends(check_rate_limit)] is applied at the route decorator level (it does not return a value, it only raises RateLimitError if the limit is exceeded), while user: dict = Depends(get_current_user) is applied as a function parameter (it returns the decoded JWT payload for use in the handler). This separation means rate limiting is checked before authentication, which is intentional: rate limiting should block excessive requests before spending CPU cycles on JWT verification.
- The document chat endpoint validates the uploaded file by checking file.filename.lower().endswith(".pdf") before processing. This client-side validation is a convenience check, not a security boundary. The actual content validation happens when PyPDFLoader attempts to parse the file: a non-PDF file with a .pdf extension would fail at the parsing stage and raise a DocumentProcessingError. The alternative of validating the file's MIME type or magic bytes would provide stronger content validation but would require additional libraries (python-magic) and is unnecessary when PyPDFLoader already validates the content structure.
- Both chat endpoints measure processing time using time.perf_counter() before and after the LLM call, then compute elapsed_ms = (time.perf_counter() - start) * 1000. time.perf_counter() is used instead of time.time() because it provides the highest available resolution for measuring short durations and is not affected by system clock changes. The processing time is rounded to 2 decimal places in the response to avoid floating-point noise in the JSON output.

### Step 10 -- Data Validation with Pydantic v2 Schemas

- I defined 8 Pydantic v2 models in schemas.py covering all request and response types plus 2 audit models. The alternative was to use plain dictionaries or dataclasses. Pydantic v2 was chosen because it provides automatic JSON serialization/deserialization, field-level validation with descriptive error messages, OpenAPI schema generation for API documentation, and runtime type enforcement. Dataclasses provide type hints but no runtime validation. Plain dictionaries provide no type safety at all. Pydantic v2 specifically (over Pydantic v1) was chosen because v2 is rewritten in Rust (pydantic-core) and provides 5-50x faster validation performance, which matters for an API that validates every incoming request.
- Request models use Field(...) with min_length and max_length constraints to enforce input boundaries at the schema level, before any application logic runs. The question field in ChatRequest uses min_length=1, max_length=5000 with a @field_validator that strips whitespace and rejects blank strings. This three-layer validation (min_length check on raw input, strip whitespace, reject blank result) prevents edge cases like a question consisting entirely of spaces from reaching the LLM, which would waste inference credits on meaningless queries. The 5000-character maximum was chosen as a balance between allowing detailed questions and preventing abuse through extremely long inputs that could consume excessive LLM context window tokens.
- Response models include timestamp fields with default_factory=datetime.utcnow, processing_time_ms as a float for sub-millisecond precision, and optional session_id fields for client-side session tracking. The ErrorResponse model includes error=True as a boolean discriminator, status_code as an integer, message as a human-readable string, optional details for structured error metadata, and optional request_id for correlation. This consistent response envelope makes it straightforward for API clients to implement generic error handling logic.
- The ChatRole enum (USER, ASSISTANT, SYSTEM) is defined as a string enum for forward compatibility with multi-turn conversation features. Although not currently used in route handlers, it provides a typed vocabulary for conversation role annotations that can be leveraged when adding conversation history persistence or multi-turn session management.
- All models use Pydantic's model_config or Field-level configuration rather than the older Config inner class syntax from Pydantic v1. This ensures compatibility with Pydantic v2's new configuration API and avoids deprecation warnings.

### Step 11 -- Testing Strategy

- I chose pytest as the testing framework over unittest (Python's standard library). Pytest was selected because its fixture system provides reusable, composable test setup and teardown logic with dependency injection; it supports parameterized tests via @pytest.mark.parametrize for testing multiple inputs with a single test function; its assertion introspection provides detailed failure messages without requiring self.assertEqual-style methods; and the pytest-asyncio plugin provides native support for testing async functions. Unittest's class-based test organization (setUp, tearDown, test methods) is more verbose and less flexible than pytest's fixture-based approach.
- The conftest.py file defines 5 fixtures that form the foundation of the test suite. The _set_env fixture (autouse=True, runs for every test) monkeypatches environment variables to safe test defaults and calls get_settings.cache_clear() to force the Settings object to be recreated with the test values. Without clearing the lru_cache, the first test to call get_settings() would cache the Settings object, and all subsequent tests would use the same cached object regardless of their monkeypatched environment variables. The mock_db fixture creates a MagicMock with AsyncMock methods (connect, close, health_check) that simulates a healthy MongoDB connection without requiring an actual database. The client fixture patches both Database.__new__ and app.get_database to inject the mock_db, then creates a FastAPI TestClient. The auth_headers fixture generates a valid JWT token for the "testuser" subject, providing authenticated request headers that tests can use without reimplementing token creation logic.
- The test suite is organized into 6 modules with 46 total test cases. test_config.py (7 tests) validates Settings creation, environment enum parsing, lru_cache behavior, property accessors, and CORS origin validation. test_exceptions.py (8 tests) verifies each custom exception class produces the correct status code and message. test_schemas.py (10 tests) validates Pydantic model field constraints, default values, whitespace stripping, and rejection of invalid inputs. test_security.py (9 tests) covers JWT token creation and verification (including expired tokens and invalid signatures), rate limiter allow/deny behavior, and sanitization function output for XSS and NoSQL injection payloads. test_monitoring.py (3 tests) verifies JSON log formatting, logging setup, and audit event generation. test_api.py (9 tests) performs integration testing against the running FastAPI application via TestClient, covering the root endpoint, all health endpoints, token generation, authenticated and unauthenticated chat requests, and document upload validation.
- The testing approach uses both unit tests and integration tests. Unit tests (test_config, test_exceptions, test_schemas, test_security, test_monitoring) test individual modules in isolation with mocked dependencies. Integration tests (test_api) test the full request/response cycle through the FastAPI application with mocked database and LLM dependencies. The alternative of testing only at the integration level would miss edge cases in individual modules, while testing only at the unit level would miss issues in module interactions (middleware ordering, dependency injection wiring, exception handler registration).
- Code coverage is configured in pyproject.toml with source=src and fail_under=80, meaning the CI pipeline fails if coverage drops below 80%. The coverage report is generated in XML format and uploaded to Codecov for historical tracking and pull request annotations. The 80% threshold was chosen as a pragmatic minimum that ensures core business logic (security, LLM routing, request handling) is tested without requiring 100% coverage of boilerplate code (model definitions, configuration defaults). The alternative of 100% coverage would require testing trivial code paths (default values, property accessors) that provide minimal value relative to the testing effort.
- The mock_db fixture uses unittest.mock.MagicMock for synchronous attributes and unittest.mock.AsyncMock for async methods. AsyncMock is specifically required because FastAPI's TestClient internally runs the ASGI application through an event loop, and regular MagicMock instances do not support await. Without AsyncMock, calls like await db.health_check() would raise TypeError: object MagicMock can't be used in 'await' expression.

### Step 12 -- CI/CD Pipeline

- The GitHub Actions CI pipeline in .github/workflows/ci.yml defines three sequential jobs: lint, test, and build. The jobs are chained with needs dependencies (test needs lint, build needs test) so that a linting failure stops the pipeline before running the test suite, and a test failure stops the pipeline before building the Docker image. The alternative was to run all three jobs in parallel, but sequential execution saves CI compute time by failing fast on the cheapest check (linting) before running expensive operations (database-backed tests and Docker builds).
- The lint job runs four tools in sequence: Black --check (verifying code formatting without modifying files), Flake8 targeting src/, tests/, and app.py (enforcing PEP 8 with max-line-length=88 to match Black's default), MyPy with --ignore-missing-imports (type checking src/ while tolerating untyped third-party libraries), and Pylint with --disable=C0114,C0115,C0116 --fail-under=7 (disabling missing docstring warnings and requiring a minimum score of 7 out of 10). The combination of Black and Flake8 may seem redundant, but they serve different purposes: Black handles formatting consistency (line length, whitespace, trailing commas), while Flake8 catches logical issues (unused imports, undefined names, complexity thresholds) and style violations that Black does not address.
- The test job spins up a MongoDB 7 service container alongside the test runner. This provides a real MongoDB instance for integration tests, mapped to localhost:27017. Environment variables SECRET_KEY and GROQ_API_KEY are set to test values so that Settings validation passes. The test command runs pytest with -v for verbose output, --tb=short for concise tracebacks, --cov=src for coverage measurement, and --cov-report=xml for Codecov integration. The alternative of mocking MongoDB in CI (as the unit tests do) would miss driver compatibility issues and connection handling bugs that only manifest against a real database.
- The build job runs docker build -t genuechat:${{ github.sha }} to verify that the Dockerfile builds successfully and tags the image with the commit SHA for traceability. This does not push the image to a registry (that would be a deployment step), but it catches Dockerfile syntax errors, missing dependencies, and build failures before they reach production. The commit SHA tag ensures that every built image can be traced back to the exact source code that produced it.
- The pipeline triggers on both push to main and pull_request to main. Push triggers ensure the main branch always has a passing pipeline. Pull request triggers provide feedback to contributors before merging. The alternative of triggering only on push would allow broken code to be merged before the pipeline runs.

### Step 13 -- Containerization

- The production Dockerfile uses a multi-stage build with two stages. The first stage (builder) installs Python dependencies into a /install prefix using pip install --no-cache-dir --prefix=/install. The second stage copies only the installed packages from the builder stage (COPY --from=builder /install /usr/local) along with the application source code. This approach was chosen over a single-stage build because it produces a significantly smaller final image: the builder stage contains pip, wheel, setuptools, compiler headers, and temporary build artifacts that are not needed at runtime. A single-stage build that installs dependencies directly would retain all of these in the final image. The alternative of using Docker's --mount=type=cache for pip caching would speed up rebuilds but would not reduce final image size.
- I selected python:3.11-slim as the base image rather than python:3.11 (full Debian), python:3.11-alpine, or a distroless image. The slim variant removes documentation, man pages, and development tools from the Debian base, resulting in an approximately 120MB base image versus 900MB for the full image. Alpine was rejected because it uses musl libc instead of glibc, which causes compatibility issues with compiled Python packages (numpy, FAISS, sentence-transformers). Some packages require rebuilding C extensions against musl, which fails or produces slower binaries. Distroless images (gcr.io/distroless/python3) would be the most secure option (no shell, no package manager) but make debugging production issues significantly harder since you cannot exec into the container.
- The Dockerfile creates a dedicated genuechat user and group (groupadd -r genuechat && useradd -r -g genuechat -d /app -s /sbin/nologin genuechat) and switches to this user with the USER directive before the CMD instruction. Running as a non-root user prevents container escape attacks where a vulnerability in the application could grant root access to the host. The -r flag creates a system account (no home directory creation, no login shell), and -s /sbin/nologin prevents interactive login even if an attacker compromises the user account.
- The HEALTHCHECK directive uses a Python one-liner (python -c "import urllib.request; urllib.request.urlopen(...)") instead of curl or wget because curl is not installed in the slim base image, and installing it would add dependencies and increase image size. The health check targets /api/v1/health/live with a 30-second interval, 5-second timeout, 10-second start period (allowing the application to initialize before health checks begin), and 3 retries before marking the container as unhealthy.
- The production CMD runs Uvicorn with --workers 4 to fork 4 worker processes, each handling requests independently. This allows the application to utilize multiple CPU cores on the host machine. The alternative of using Gunicorn with Uvicorn workers (gunicorn -k uvicorn.workers.UvicornWorker) is a common recommendation, but Uvicorn's built-in --workers flag provides equivalent functionality for this use case without adding Gunicorn as an additional dependency.
- The development Dockerfile (Dockerfile.dev) is deliberately kept simple: a single stage that installs both production and development dependencies and runs Uvicorn with --reload. The source code is not copied into the image because it is bind-mounted via Docker Compose volumes, allowing file changes on the host to trigger hot-reloads inside the container without rebuilding the image.

### Step 14 -- Docker Compose Development Environment

- The docker-compose.yml defines four services (app, mongodb, prometheus, grafana) that together provide the complete development stack with a single docker compose up --build command. The alternative of running each service manually (mongod on the host, python app.py, prometheus, grafana) would require installing and configuring each tool individually. Docker Compose encapsulates the entire environment in a reproducible configuration file.
- The app service uses Dockerfile.dev (which includes development dependencies and enables --reload) rather than the production Dockerfile. The source code is mounted as a volume (- .:/app) so that file changes on the host are immediately reflected in the container without rebuilding. The depends_on directive with condition: service_healthy ensures the app container does not start until MongoDB's health check (mongosh --eval "db.adminCommand('ping')") passes, preventing startup race conditions where the app attempts to connect before MongoDB is ready.
- MongoDB uses the official mongo:7 image with a named volume (mongo_data) for data persistence across container restarts. Without the volume, all data would be lost when the container is recreated. The health check runs every 10 seconds with a 5-second timeout and 5 retries, ensuring that the depends_on health condition accurately reflects database readiness.
- Prometheus is configured with a read-only bind mount of monitoring/prometheus.yml, which defines a single scrape job targeting app:8000/metrics with a 15-second scrape interval. Docker Compose's internal DNS resolves "app" to the application container's IP. Grafana is configured with auto-provisioned datasources (pointing to http://prometheus:9090) and dashboard providers via read-only bind mounts of the monitoring/grafana/provisioning directory. The default admin credentials (admin/admin) are set via environment variables for development convenience. The read-only mounts (:ro) prevent the containers from accidentally modifying the configuration files on the host.
- All services use restart: unless-stopped, which automatically restarts containers after crashes but respects manual stops. The alternative restart policies are "no" (never restart, unsuitable for development where crashes should auto-recover), "always" (restarts even after manual stop, inconvenient), and "on-failure" (only restarts on non-zero exit codes, does not cover OOM kills which have exit code 137).

### Step 15 -- Kubernetes Deployment

- The Kubernetes manifests in k8s/deployment.yaml define five resources in a single file, separated by --- document delimiters. I chose to keep all resources in one file for simplicity of deployment (kubectl apply -f deployment.yaml provisions everything). The alternative of splitting into separate files (deployment.yaml, service.yaml, hpa.yaml, networkpolicy.yaml, ingress.yaml) would provide better organizational clarity for larger projects but adds file management overhead for a five-resource deployment. For production use with Helm or Kustomize, the manifests would be split into templates.
- The Deployment specifies replicas: 2 as the baseline, with a HorizontalPodAutoscaler (HPA) scaling between 2 and 10 replicas based on CPU utilization (70% target) and memory utilization (80% target). The HPA uses the autoscaling/v2 API which supports multiple metrics simultaneously, unlike autoscaling/v1 which supports only CPU. The dual-metric scaling ensures that memory-intensive operations (FAISS indexing, embedding generation) trigger scale-out even if CPU utilization remains low. The minimum of 2 replicas ensures high availability: if one pod fails or is being updated, the other continues serving traffic.
- Resource requests (250m CPU, 256Mi memory) and limits (1 CPU, 512Mi memory) are set on the container spec. Requests determine scheduling (the Kubernetes scheduler places the pod on a node with at least 250m CPU and 256Mi memory available), while limits enforce runtime caps (the container is CPU-throttled above 1 CPU and OOM-killed above 512Mi). The alternative of not setting resource limits would allow a single pod to consume all node resources, potentially starving other workloads. The 2:1 ratio between limits and requests provides burst capacity for LLM inference spikes while preventing runaway resource consumption.
- The pod security context sets runAsNonRoot: true and runAsUser: 1000, enforcing that the container process cannot run as root even if the Dockerfile's USER directive is removed or overridden. This is a defense-in-depth measure that complements the non-root user in the Dockerfile.
- Pod annotations include prometheus.io/scrape: "true", prometheus.io/port: "8000", and prometheus.io/path: "/metrics". These annotations allow a Prometheus instance running in the same cluster (configured with kubernetes_sd_configs for pod discovery) to automatically detect and scrape the GenueChat pods without manual scrape target configuration. This is the standard Prometheus service discovery pattern for Kubernetes.
- The liveness probe targets GET /api/v1/health/live with initialDelaySeconds: 10 (giving the application time to start before probing begins) and periodSeconds: 15. The readiness probe targets GET /api/v1/health/ready with initialDelaySeconds: 5 and periodSeconds: 10. The readiness probe has a shorter initial delay because it should start checking database connectivity as soon as possible to route traffic only to healthy pods. If the readiness probe fails, Kubernetes removes the pod from the Service's endpoint list, preventing traffic from reaching a pod that cannot serve requests. If the liveness probe fails three consecutive times, Kubernetes restarts the pod.
- The Service uses type: ClusterIP (internal-only, not exposed externally) with port 80 mapping to targetPort 8000. ClusterIP was chosen over NodePort (which exposes a port on every cluster node) or LoadBalancer (which provisions a cloud load balancer) because external access is handled by the Ingress resource. ClusterIP is the most restrictive and appropriate Service type when an Ingress controller is present.
- The NetworkPolicy restricts ingress to only pods with the label app: genuechat-ingress on port 8000, and restricts egress to MongoDB pods on port 27017 and any destination on port 443 (for outbound HTTPS calls to the Groq API). All other network traffic is denied. The alternative of no NetworkPolicy would allow unrestricted pod-to-pod communication within the cluster, which violates the principle of least privilege. The egress rule for port 443 is deliberately broad (to: []) to allow connections to any external HTTPS endpoint, because the Groq API endpoint may change and hardcoding IP ranges would be fragile.
- The Ingress resource uses the nginx IngressClass with TLS termination via a genuechat-tls Secret and host-based routing on genuechat.example.com. Annotations enable SSL redirect (all HTTP traffic is redirected to HTTPS) and Nginx-level rate limiting (100 requests per second) as an additional defense layer on top of the application-level rate limiter. The application-level rate limiter protects against abuse from authenticated clients, while the Nginx rate limiter protects against volumetric attacks that target unauthenticated endpoints like the token generation route.

### Step 16 -- Pre-Commit Hooks and Code Quality Enforcement

- The .pre-commit-config.yaml configures four hooks that run automatically before every git commit. Black (v24.4.2) reformats all Python files to a consistent style with 88-character line length. Flake8 (v7.0.0) with the flake8-bugbear plugin catches common bugs and PEP 8 violations. MyPy (v1.10.0) performs static type checking. Standard hooks from pre-commit-hooks handle trailing whitespace removal, end-of-file newline enforcement, YAML syntax validation, and rejection of files larger than 500KB (preventing accidental commits of binary blobs, datasets, or model weights).
- The pre-commit framework was chosen over alternatives like Husky (JavaScript ecosystem, not native to Python) or manual git hooks (fragile, not version-controlled). Pre-commit manages hook installation, version pinning, and virtual environment isolation for each hook, ensuring that all developers run the same tool versions regardless of their local Python environment.
- The 500KB file size limit on check-added-large-files prevents accidental commits of model weight files (which can be hundreds of megabytes), PDF test fixtures, database dumps, or other binary files that should not be stored in git. The alternative of using a .gitignore entry would only prevent untracked files from being committed, not files explicitly added with git add.
- The Pylint threshold is set to --fail-under=7 rather than the maximum 10 because some Pylint conventions (missing module docstrings C0114, missing class docstrings C0115, missing method docstrings C0116, too few public methods R0903) conflict with the project's coding style. Disabling these specific checks while maintaining a score threshold of 7 ensures that meaningful code quality issues (undefined variables, unused imports, circular dependencies) still cause failures while allowing reasonable deviations from Pylint's default style preferences.
- The flake8-bugbear plugin was included alongside base Flake8 because it catches additional issues that base Flake8 misses, such as mutable default arguments in function signatures (B006), redundant exception types in except blocks (B014), and calls to getattr with constant attribute names (B009). These are common sources of bugs in Python code that are not covered by PEP 8 style checking alone.
